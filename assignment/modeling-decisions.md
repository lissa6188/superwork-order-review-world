# 애매한 모델링 결정

좋은 모델러는 애매함을 없애는 사람이 아니라, **애매함을 알아채고 이유 있게 결정하는 사람**입니다.
하나의 개념이 여러 방식으로 모델링될 수 있을 때, 그 결정을 기록하세요.

최소 요건: **2개 이상.**

## 흔한 예

| 개념 | 가능한 모델링 |
|---|---|
| 승인 (Approval) | State(승인됨) · Transition(승인하다) · 별도 Entity(승인 기록) |
| 위험 평가 (Risk Assessment) | 별도 Entity · Attribute(위험 점수) |
| 약점 (Weak Point) | Entity · Attribute · 파생된 State |
| 법무 검토 (Legal Review) | State(검토 중) · 별도의 Work(담당자 · 마감이 있는 일) |

## 결정 1

- **개념:** 검토규칙근거 (과거 검토의견서 한 건이 검토규칙을 지지하거나 반대하는 기록)
- **고려한 대안:** (최소 2개)
  - 별도 Entity — 검토규칙 하나에 근거 덱이 여러 건이라 하위 테이블처럼 뺀다.
  - Event / World 밖 기록 — 근거는 기록만 하고, World에는 검토규칙의 지지 근거 수, 반대 근거 수만 둔다.
- **최종 선택:** Event / World 밖 기록. 처음엔 Entity로 정했다가 같은 날 번복했습니다.
- **이유:** 근거 한 건은 한 번 기록되면 끝나는 사실이라 옮겨 다닐 상태가 없습니다. 일치 여부를 사람이 건마다 확인하게 만들면 병목이 생기는데, 그럴 이유가 없었습니다. 그리고 DSL에는 집계가 없어서 "같음 근거 ≥ N" 같은 guard를 근거 레코드로는 쓸 수 없고, 결국 검토규칙에 기록된 숫자를 봐야 합니다. 같은 근거가 반대 근거로도 세어지면 안 되니까 지지와 반대를 나눠서 기록했습니다.
- **ESTC에 미친 영향:**
  - Entity: 검토규칙근거 Entity를 뺐습니다.
  - State: 없음.
  - Transition: 없음.
  - Constraint: 검토규칙에 `supporting_evidence_count`, `opposing_evidence_count`를 두고, `C3_rule_has_opposing_evidence`(재검수), `C13_rule_has_supporting_evidence`(확정, break-fix에서 추가)가 이 숫자를 봅니다.

## 결정 2

- **개념:** 신규 검토규칙이 생겼을 때 운영 중인 검토규칙세트를 어떻게 하나 (학습과 운영의 관계)
- **고려한 대안:**
  - 세트 하나가 상태를 오간다 — 신규 규칙이 생기면 운영 중인 세트를 학습 중으로 되돌리고, 다시 전환 승인을 받는다.
  - 학습과 운영을 따로 돌린다 — 운영 중인 세트(v1)는 그대로 쓰고, 신규 규칙은 새 버전 세트(v2, 학습 중)에 쌓는다. v2가 승인되면 v1은 대체된다.
- **최종 선택:** 학습과 운영을 따로 돌립니다.
- **이유:** 첫 번째 방식은 후보 규칙 하나만 생겨도 운영 전체가 멈추고 사람이 다시 승인해야 합니다. 저는 실패나 변경은 되돌리지 않고 새로 만든다는 원칙으로 설계했고, 이렇게 하니 세트에 버전이 있는 이유도 명확해지고 세트를 선택하고 폐기하는 흐름도 자연스러워졌습니다. 새 규칙이 검증되는 동안에도 기존 세트로 초안 작성은 계속됩니다. 케이스는 접수할 때 운영 중인 세트를 고정해서 물고 가고, 진행 중인 초안은 세트가 대체돼도 그대로 갑니다.
- **ESTC에 미친 영향:**
  - Entity: 케이스에 `rule_set`(ref), `applied_set_version`을 둡니다.
  - State: 검토규칙세트에 끝 상태 `set_replaced`를 추가했습니다.
  - Transition: 운영 중에서 학습 중으로 되돌아가는 전이를 지우고, 운영 중인 세트를 대체됨으로 보내는 `set_replace`를 추가했습니다. 순서는 v2가 전환 승인을 받는 시점에 v1을 먼저 대체하고 그다음 v2를 운영 중으로 바꿉니다. 반대 순서면 운영 중인 세트가 잠시 둘이 됩니다.
  - Constraint: 식에는 "ref가 비어 있지 않다"를 쓸 방법이 없어서(null이 없음), "세트 ref 지정됨" 대신 `case_extract`에서 `C10_case_set_activated`로 세트가 운영 중인지 확인합니다. "운영 중인 세트는 하나뿐"은 식에 개수를 세는 문법이 없어서 전이 순서로 지킵니다. `set_replace`에는 guard가 없어서 이 순서를 World가 강제하지는 못합니다 — 알고 남겨 둔 빈틈입니다.

## 결정 3

- **개념:** 신규 없이 연속 분석한 덱 수의 갱신 — 전환 반려 후, 그리고 덱 분석 후
- **고려한 대안:**
  - World 밖에서 갱신 — 식에 산술이 없으니 카운트는 실행 쪽이 알아서 바꾸고, World는 비교만 한다.
  - World에 effect로 선언 — 값이 바뀌는 순간을 해당 transition의 `effects`에 이름으로 적는다.
- **최종 선택:** effect로 선언합니다.
  - `set_reject`(전환 반려)에 `effects: [reset_decks_since_new_rule_count]`를 붙였습니다. 반려하면 신규 없이 연속 분석한 덱 수를 0으로 되돌립니다.
  - 덱 분석 완료는 전이를 둘로 나눴습니다. `deck_analyze_new_rule`(신규 후보 > 0)은 연속 덱 수를 0으로 되돌리고 검수대기 수를 늘리고, `deck_analyze_no_new_rule`(신규 후보 == 0)은 연속 덱 수를 +1 합니다.
- **이유:** 반려 후에도 값이 그대로면 이미 전환 기준(≥ 3)을 넘은 상태라서 에이전트가 곧바로 다시 승인 요청을 하게 되고, 요청과 반려가 반복됩니다. 0으로 되돌리면 "학습 덱을 3건 더 분석한다"가 자연스럽게 다음 할 일이 됩니다. 값이 언제 바뀌는지가 World에 드러나야 guard가 읽는 값을 믿을 수 있습니다. effects는 조건을 쓸 수 없는 이름 목록이라서, 분석 결과에 따라 결과가 달라지는 경우는 조건을 guard로, 결과를 전이별 effects로 나눴습니다.
  - 주의: v1 규격에는 effect의 본문(무엇을 어떻게 바꾸나)을 정의하는 칸이 없습니다. World는 "이 전이가 이 효과를 일으킨다"까지만 선언하고, 실제로 값을 0으로 바꾸는 코드는 런타임(실행 쪽 도구)이 맡습니다. 그래서 effect 이름만 보고도 무엇이 바뀌는지 알 수 있게 지었습니다. validate는 effect 이름을 검사하지 않아서, 작성 중에 `deck_analyze_no_new_rule`에 reset을 잘못 넣었는데도 PASS가 나왔습니다. 그대로 뒀으면 연속 덱 수가 늘 0이 되어 세트가 영원히 운영으로 못 넘어갔을 겁니다.
- **ESTC에 미친 영향:**
  - Entity: 학습 덱에 `rule_set`(ref)이 필요해졌습니다. effect가 어느 세트의 값을 바꾸는지 가리켜야 하기 때문입니다.
  - State: 없음.
  - Transition: 덱 분석 완료 전이가 2개가 됐고, `set_reject`, 검토규칙 전이, 덱 분석 전이에 effects가 붙었습니다.
  - Constraint: `C1_set_stable`(연속 덱 수 ≥ 3)과 `C2_set_no_pending_review`(검수대기 == 0)가 이 값들을 읽습니다. 처음엔 둘을 승인 요청에 and로 걸었는데 조건이 너무 강해서, 승인 요청에는 C1만, 승인에는 C2만 걸었습니다.

## 결정 4

- **개념:** 이미 분석한 덱을 다시 분석하는 재분석 덱
- **고려한 대안:**
  - 재등록을 허용한다 — 학습 덱에 `원본 덱`(ref)과 `is_reanalysis` 칸을 두고, 재분석 덱은 연속 덱 수를 올리지 않도록 분석 전이를 3개로 나눈다.
  - 재분석 덱을 빼고, 이미 분석한 덱은 다시 등록하지 않는다(World 밖 운영 규칙).
- **최종 선택:** 재분석 덱을 뺍니다.
- **이유:** 심플 이즈 베스트. 재분석 덱을 구분하려면 칸 하나와 전이 하나가 더 필요하고 조건도 복잡해집니다. 같은 덱을 두 번 등록해서 연속 덱 수를 채우는 공격은 World가 막지 못하는데, 이건 알고 남겨 둔 빈틈입니다.
- **ESTC에 미친 영향:**
  - Entity: 학습 덱에서 `원본 덱` 칸을 지웠습니다.
  - State: 없음.
  - Transition: 분석 전이는 2개로 유지합니다.
  - Constraint: 없음.

## 결정 5

- **개념:** 식(expr)에서 Entity와 예/아니오 값을 쓰는 방법
- **고려한 대안:**
  - 리포 예시처럼 식에서 Entity를 소문자로 쓰고(`request.amount`), 예/아니오는 bool 타입으로 둔다.
  - 식에도 Entity 이름을 그대로 쓰고(`ReviewRuleSet.decks_since_new_rule_count`), 예/아니오는 문자열 `"yes"`/`"no"`로 비교한다.
- **최종 선택:** 두 번째입니다.
- **이유:** Entity 이름과 식의 표기가 대소문자만 달라지면 개발자 입장에서 헷갈립니다. validate도 통과합니다. 그리고 식 파서를 직접 확인해 보니 `true`/`false` 값이 없어서, `== true`라고 쓰면 `true`를 값이 아니라 경로 이름으로 읽습니다. 그래서 문자열로 비교하고 seed에도 `"yes"`처럼 따옴표를 붙였습니다. Studio가 이 표기를 어떻게 해석할지는 리뷰에서 확인할 부분입니다.
- **ESTC에 미친 영향:**
  - Entity: `has_opinion_slide`, `extraction_verified`를 string(yes/no)으로 뒀습니다.
  - State: 없음.
  - Transition: 없음.
  - Constraint: C4, C5, C8, C9, C11이 `== "yes"`/`== "no"`로 비교합니다.
