# Entity 결정 — 가장 중요한 과제

업무 설명에 등장하는 **후보 개념**을 모두 적고, 하나씩 **최종 분류**와 **이유**를 결정합니다.
AI가 제안할 수는 있지만, 분류를 결정하고 이유를 쓰는 사람은 여러분입니다.

## 분류

| 분류 | 뜻 | 예 |
|---|---|---|
| **Entity** | 고유한 정체성을 갖고 시간이 지나도 추적되는 것 | 계약, 주문, 학생 |
| **Role** | 행동하는 주체의 역할 | 요청자, 승인자, 트레이더 |
| **Attribute** | 어떤 Entity에 기록되는 값 | 금액, 마감일, 수량 |
| **State** | Entity가 흐름 속 어디에 있는가 | 제출됨, 승인됨, 체결됨 |
| **Transition** | 상태를 바꾸는 허용된 행동 | 제출, 승인, 서명 |
| **Constraint** | 행동을 허용하거나 막는 규칙 | 셀프 승인 금지, 금액 한도 |
| **Event / Effect** | 일어난 일, 또는 World 밖으로 나가는 효과 | 이메일 발송, 브로커 주문 전송 |
| **제외** | 이 World에 필요 없는 것 | |

## Entity 판단 체크리스트 (교육용)

어떤 개념이 Entity인지 헷갈리면 다음을 물어보세요. 모두 "예"일 필요는 없지만,
"예"가 거의 없다면 Attribute · State · Role일 가능성이 큽니다.

1. **고유한 정체성**이 있는가? (각각을 구별해서 가리킬 수 있는가 — "이 계약", "저 계약")
2. **여러 단계에 걸쳐 지속**되는가?
3. 시간이 지나며 **의미 있는 상태**를 갖는가?
4. 다른 개념과 **중요한 관계**를 맺는가?
5. **행동이 그것에 작용**하는가? (누군가 그것을 승인 · 서명 · 체결 · 채점한다)
6. **정책이 그것을 가리키는가?** ("금액이 5,000을 넘는 요청은 …")

## 결정 기록

최소 요건: 최종 **Entity 3개 이상**, Entity가 **아닌** 개념 **2개 이상** — 각각 이유 포함.

| 후보 개념 | 최종 분류 | 이유 (체크리스트 중 무엇이 결정적이었나) |
|---|---|---|
| 검토규칙 | **Entity** (`ReviewRule`) | 3번 의미 있는 상태가 결정적이었습니다. 후보로 생성된 후 검수를 거쳐 확정되고, 반대 근거가 쌓이면 재검수되어 폐기될 수도 있습니다. 5번 에이전트가 후보를 만들고 검수자가 확정하는 행동이 작용하고, 6번 "반대 근거가 있어야 재검수할 수 있다"는 정책도 이것을 가리킵니다. 그냥 "규칙"이라고 하면 World의 constraint와 헷갈려서 이름을 검토규칙으로 정했습니다. |
| 검토규칙세트 | **Entity** (`ReviewRuleSet`) | 2번 여러 단계에 걸쳐 지속되고 3번 학습 중에서 전환 검토 중을 거쳐 운영 중이 되고, 다음 버전이 운영되면 대체됨으로 끝나며 상태가 바뀝니다. 6번 "운영 중인 세트로만 검토의견서 초안을 작성한다"는 정책이 이것을 가리킵니다. 처음엔 "규칙집"이라고 불렀는데 문서 한 장처럼 들려서, 상태를 갖고 자라는 대상이라는 뜻이 드러나게 검토규칙세트로 바꿨습니다. |
| 학습 덱 | **Entity** (`LearningDeck`) | 5번 에이전트가 직접 추출하고 분석하는 대상이고, 4번 분석이 끝나면 검토규칙세트의 카운트(분석한 덱 수, 신규 없이 연속 분석한 덱 수)가 바뀝니다. 의견서 슬라이드가 없는 덱은 학습 제외라는 정상 상태로 둡니다. |
| 수주심의 요청 케이스 | **Entity** (`OrderAcceptanceCase`) | 5번 에이전트가 초안을 작성하고 발송하는 대상이고, 4번 학습 쪽 Entity와 처음 이어지는 지점입니다. 접수할 때 운영 중인 검토규칙세트를 물고 시작하고, 발송 실패도 상태로 남겨서 재발송을 3회까지 시도합니다. |
| 검토규칙근거 (과거 의견서 한 건이 규칙을 지지하거나 반대하는 기록) | **Event** / World 밖 기록 | 처음엔 검토규칙 하나에 근거 덱이 여러 건이라 Entity로 정했다가 번복했습니다. 3번 근거 한 건은 한 번 기록되는 사실이라 옮겨 다닐 상태가 없고, 4번 다른 것이 이것을 가리키지 않습니다. 6번 DSL에 집계가 없어서 정책은 근거 레코드가 아니라 검토규칙에 기록된 지지 근거 수, 반대 근거 수를 봅니다. |
| 접수자 | **Attribute** (케이스의 `requester`) | 처음엔 principal로 봤는데, 접수자는 World 안에서 전이를 일으키지 않고 초안 메일을 받기만 합니다. 그래서 케이스에 누구에게 보낼지만 기록합니다. 사람의 소속이나 상관을 따라갈 필요가 없어서 Employee Entity도 두지 않았습니다. |
| 검수자, 전환 승인자 | **Role** (`rule_reviewer`, `set_approver`) | 행동하는 주체의 역할입니다. 검수자는 빌더(에이전트 아키텍트), 전환 승인자는 이 프로젝트를 요구한 실무담당자로 서로 다른 사람입니다. 나중에 검수자를 실무자로 넘길 때는 principals 블록만 고치고 world.version을 올립니다. |
| 학습 에이전트, 초안 에이전트 | **Role** (`rule_learner`, `review_drafter`) | 에이전트도 principal입니다. 학습과 운영은 필요한 스킬이 달라서 둘로 나눴고, 역할이 나뉘어 있으니 초안 에이전트가 검토규칙이나 세트를 건드리는 일은 World가 막습니다. |
| 보류 | **State** (`rule_on_hold`) | 기준값이 없거나 지침끼리 충돌해서 지금은 확정할 수 없는 검토규칙이 머무는 위치입니다. 덱에 자료가 없어서 내는 「확인 불가」와는 다른 개념입니다. |
| 확인 불가, Risk, 유의 | **Attribute** 값 (`result_type`) | 검토규칙이 적용됐을 때 내는 결과의 종류입니다. 등급 없이 수치를 인용하거나 원문을 기재하는 규칙도 있어서 이름을 "판정등급"에서 결과유형으로 바꿨습니다. |
| 검토의견서 메일 발송 | **Effect** (`send_review_email`) | World 밖으로 나가는 첫 효과입니다. 되돌릴 수 없어서 발송 시도 횟수 < 3 guard를 걸었습니다. |
| 고객사, 제품, 수주유형 | **제외** | 검토규칙을 적용할 때 에이전트가 덱에서 읽는 내용이지 World의 guard가 쓰는 값이 아닙니다. 실제 회사 정보라 익명화 측면에서도 넣지 않았습니다. |

## 주인공 Entity

상태기계를 갖는 Entity(`owned_state: true`) 하나를 고르세요. 이 World의 **Work** 입니다.

- 주인공 Entity: 4개 모두 상태기계를 갖습니다 — 검토규칙세트, 검토규칙, 학습 덱, 수주심의 요청 케이스.
- 왜 이것인가: 템플릿은 하나로 시작하라고 하지만, 하나로 시작해서 validate하고 하나씩 늘려 가는 방식으로 작성했습니다. 이 과제는 제 실제 프로젝트이기도 하고, 제 아키텍처에서는 상태기계가 하나가 아니라 서로 맞물려 돌아갑니다. 학습 덱이 분석되면 검토규칙세트의 카운트가 바뀌고, 검토규칙이 검수되면 세트의 검수대기 수가 바뀌고, 세트가 운영 중이어야 케이스가 진행됩니다. 이 의도를 다 작성하고 보는 게 맞다고 판단했습니다.
